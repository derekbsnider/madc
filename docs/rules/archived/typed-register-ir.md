# Typed-Register IR — Reasoning

## Why the IR exists

Before the IR, every `TokenXxx::compile()` method had to solve the same
four-axis decision from scratch each time:

1. Is the value in a **register** (Gp/Xmm), at a **memory location**,
   a **compile-time constant**, or behind a **pointer**?
2. What is its **type** (int8..int64, uint8..uint64, float, double,
   string, pointer-to-X, ...)?
3. What is the **caller's** destination shape?
4. What **conversion** is needed to bridge the source and destination?

A bug is one forgotten axis away. Nearly every silent-codegen issue in
the last six months has fit that shape:

- `*e == 0` — `safecmp` got a Mem instead of a Reg.
- `int r = a < b;` — `TokenLT` passed a Mem setcc destination.
- `v.x += 2.5;` on a struct-member double — `resolveCompoundLHS`
  loaded into a Gpq regardless of type.
- `**pp = v;` — the LHS chain assumed `ttMember` implied TokenMember.
- `printf("%f", float_var)` — variadic call site didn't cvtss2sd
  before the ABI-expected double slot.

Each fix added a special case to *one* compile method. The cluster is
generated by the absence of a shared ground truth about what shape a
value has at each point. The IR *is* that ground truth.

## Design choices

### Emit-as-you-build, not deferred

Two plausible designs:

- **Deferred** — build an IR graph first, emit asmjit at the end.
  Enables future optimization (DCE, CSE, constant folding, LICM).
- **Emit-as-you-build** — each `IRBuilder::load` / `store` / `coerce`
  call emits asmjit immediately and returns an IRValue describing
  the result.

We chose emit-as-you-build because the IR's reason to exist is
*correctness of shape/type decisions*, not optimization. Deferred
emission adds node lifetime, a second pass, and arena allocation
complexity for benefits madc doesn't need today. If an optimization
phase becomes worthwhile later, we can refactor — the builder API
itself doesn't need to change.

### Four shapes, no more

`IRShape` is `Reg`, `Mem`, `Imm`, `Addr`. That covers every place
asmjit already cares about the distinction. Adding more shapes
(e.g. a separate `XmmReg` vs `GpReg`) would duplicate information
already in the DataDef (`type->is_real()`). Keep the shape set
minimal so the dispatch tree in `IRBuilder` stays readable.

### No phi, no dominance, no our-own-allocator

The proposal is explicitly *not* SSA. asmjit's Compiler already does
virtual-register allocation and spilling — and does it well. madc's
bugs aren't register-allocation bugs. They're shape-coercion bugs.
Fixing the allocator wouldn't help; adding dominance-and-phi infra
would add months of work and a new class of bugs without closing the
one we have.

### IRBuilder carries a Compiler reference, not a full Program

The builder needs `asmjit::x86::Compiler` to emit instructions. It
does NOT need the full `Program` state (symbol maps, datatype_map,
namespace_map, etc.). Keeping the dependency narrow means:

- The builder is unit-testable in isolation (see `test_ir.cpp`).
- We can instantiate builders in test fixtures without standing up
  a full parse context.
- Future refactors of `Program` don't require touching the IR.

## What the IR does NOT do (yet)

- **No BinOp / Cmp / Call / Branch in Stage 0.** Those land as tokens
  are ported. Stage 0 is just Load / Store / Coerce — the absolute
  minimum to validate the design.
- **No integer ↔ real conversion.** `coerce()` throws if asked.
  Stage 2 will add `cvtsi2sd` / `cvtsd2si` when the first arithmetic
  token is ported.
- **No string coercion.** `dtSTRING → const char *` lives in
  `TokenCallFunc::compile` today via `string_cstr`. That moves into
  `IRBuilder::coerce` in Stage 3 when calls are ported.
- **No pointer-scaled arithmetic.** `p + n` on `T *` needs
  `n * sizeof(T)` scaling; Stage 2 will add a helper when TokenAdd
  is ported.

Every "not yet" is a place where the IR can grow in one obvious
spot instead of 40 scattered compile methods re-inventing it.

## Migration staging

1. **Stage 0 — scaffolding.** This commit. IR types, builder
   skeleton, Load/Store/Coerce, unit tests. No token changes. 170
   integration tests stay green by not touching their code paths.
2. **Stage 1 — leaves.** Port `TokenInt`, `TokenReal`, `TokenChar`,
   `TokenVar`, `TokenAddrOf`, `TokenDeref`, `TokenDerefExpr`,
   `TokenMember`, `TokenSubscript`. These produce values; porting
   them exercises Load / Coerce and forces `IRValue` to flow out of
   `compile()` for the first time.
3. **Stage 2 — arithmetic.** Binary ops, comparison, compound-
   assignment. `safeadd` / `safecmp` / `safemul` collapse into
   `IRBuilder::binop` / `cmp`. `resolveCompoundLHS` is deleted
   (the IR makes its decisions explicit upstream).
4. **Stage 3 — calls.** `TokenCallFunc`, the dlsym variadic path,
   multi-return, struct-member-fn-pointer dispatch. Varargs
   promotion (`cvtss2sd` before printf) moves into
   `IRBuilder::call_arg`.
5. **Stage 4 — control flow.** `TokenIf`, `TokenFor`, `TokenWhile`,
   `TokenDo`, `TokenSwitch`, `TokenTerQ`. Labels and branches become
   IR nodes. The `regdp` reset rule (`.claude/rules/regdp-reset.md`)
   becomes unnecessary because the IR owns dataflow between sub-
   expressions.
6. **Stage 5 — cleanup.** Remove the now-unused parts of
   `typesafe.cpp`. `safemov` / `safeadd` / etc. either shrink to
   one-liners inside `IRBuilder` method bodies or disappear
   entirely.

At every stage, `make -C src fulltest` must stay green. A port that
regresses a test is reverted, investigated, and re-tried — never
papered over with a compat shim in the builder.

## Cost model

- **Runtime overhead: 0%.** The IR emits the same asmjit calls; the
  same x86 is produced.
- **Compile-time overhead: <10%.** One extra function call per
  shape/type transition. madc's compile time is dominated by
  asmjit's register allocator and x86 encoding; a few more
  function frames vanish in the noise.
- **Code size: +500–800 net LOC.** Scaffolding adds ~1000 LOC;
  simplifications in `typesafe.cpp`, `compiler.cpp`, and
  `resolveCompoundLHS` remove several hundred.
- **Dev time: 4–6 weeks, in parallel with MadSMAUG porting.**
  SMAUG work hits IR-ported code paths first and thereby
  validates them.

## When this was wrong

If this document exists and the IR is landed but the bug rate on
compose-related operand shapes hasn't dropped, the IR is failing at
its job. Before extending the IR further, audit the remaining bugs:
are they genuinely new shape compositions, or are they in parts of
the codebase the IR hasn't reached yet? If the former, the design
needs rethinking; if the latter, finish the migration.
