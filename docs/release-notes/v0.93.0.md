# Release v0.93.0 — 2026-08-20

Floating-point codegen at gcc speed. An investigation into why donut.c
animated visibly slower under madc than under gcc -O0 — despite identical
dynamic instruction counts — found a six-year-old defect in upstream
MIR's x86-64 generator, fixed here in the in-tree fork.

- **Call-heavy FP code runs ~2.8× faster; donut.c now beats gcc -O0**
  (300 frames: 1.374s → 0.493s vs gcc -O0's 0.514s, outputs
  byte-identical).
- Root cause: the merging scalar SSE converts (`cvtsi2ss`, `cvtsi2sd`,
  `cvtss2sd`, `cvtsd2ss`) were emitted bare, creating a false output
  dependency on the destination register's previous writer — in
  sin/cos-heavy loops, the previous libm call's return chain. Successive
  calls serialized on full latency (~76 cycles/call) instead of
  overlapping (~24), invisible to instruction-counting profilers.
- Fix: the dependency-breaking idiom gcc and clang emit — `pxor dst,dst`
  before the convert — added to the generator's pattern table, with the
  tied dst==src forms keeping the bare encoding (a real dependency).
- The defect is pure upstream MIR code (patterns unchanged since 2019)
  and affects every MIR user's FP workloads; an upstream PR is queued
  behind owner review.
- Validation: MIR c2mir-gen-test at its exact baseline (1143/2286/0),
  fulltest 1104/0/0/9, EXE lane 1063/0, all reducer outputs
  md5-identical, no regression on the already-fast microbenchmarks.
