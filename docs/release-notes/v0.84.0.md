# Release v0.84.0 — 2026-08-17

The forest pack has always been able to degrade quietly: it exits 0 while
tolerating parse failures, and a bind can lose an entire aggregate without a
word. Task #64 was exactly that and it shipped — a class-nested enum tag stamped
a type-id and never recorded, which cost `std::ios_base` and the whole darwin
iostream family. v0.82.0 added the diagnostics that name the class; this release
adds the gate that reads them, over all three packs, with per-profile baselines.

It paid for itself on its first real run, which is the argument for gates that
read what the build already prints: a `long double` member had been vanishing
from any struct bound out of a container, and both macOS artifacts turn out to
ship with no MIR cache blob at all.

- **One owner, three packs.** `scripts/forest_pack_gate.sh` is called by
  `forest_pack.sh` (linux), `forest_pack_windows.sh` (win64) and
  `forest_pack_darwin.sh` (darwin, once per arch) on each run's own captured log.
- **Per-profile baselines**, because the number carried in the hand-off was the
  *darwin* one: the macOS log splits into 58 + 58 at its two pack-OK lines, while
  linux and win64 both read 93 over libstdc++ classes that share almost nothing
  with libc++'s. One number for all three would have been 35 free slots for
  regressions.
- **Counting anchored on the diagnostic's own shape.** On one linux pack log
  `grep -c error` says 339 (it matches `filesystem_error` inside deliberate
  `pack drop:` lines), `grep -c 'error:'` says 102 (it matches
  `system_error:616:6:` in a path), and `: error: ` over an ANSI-stripped stream
  says 93.
- **Hard zero for the two losses with no legitimate instance** —
  `materialize fill: DROPPED` and `forest_restore_decls: SKIPPED`, each a record
  the consumer admitted and then could not use, with no live parse to rescue it.
  The DK_NONE census, closure drops and MIR-blob skips ratchet instead: measuring
  showed 55 of 57 `kind=0` cross-references are legitimate dependent operands, so
  a hard zero there would have gone red on day one on correct code.
- **No verdict without evidence of a bind.** Every load-side diagnostic is
  `DBG`-gated, so a run that materialized nothing would score a clean sweep of
  zeros; the gate requires the `materialize filter:` marker first.
- **A `long double` member vanished at bind.** Slot 18 was still "reserved" after
  real long double landed in v0.78.0, so the freeze minted it a project id no
  record walk writes. A struct with a `long double` member lost that member when
  bound — live printed the g++/clang answer, bind reported
  `Unidentified member 'lo'`. Pinning the slot also cleared every closure drop on
  both packs, so containers now carry strictly more than they did.
- **Both macOS packs ship with no MIR cache blob** (linux packs 467 KB, win64
  497 KB). Pre-existing and correctness-preserving — which is why it exited 0 —
  but every consumer compile on macOS pays full price. Now baselined with both
  causes and reducer shapes recorded instead of silent.
- **A pre-merge `/dupaudit` consolidation:** "every listed entry point must be a
  unit" was implemented in the win64 and darwin packs and **absent from linux**,
  the lane every other lane is measured against. Now one owner, with literal
  matching and two properties the inlined loops lacked — a list that verifies
  nothing fails, and an entry point is never satisfied by a substring.
- **17 hermetic selftest legs** wired into `fulltest`, covering both directions
  of every boundary. Two of them exist because the harness caught itself first:
  expect-RED legs were passing on `rc=126` from a missing exec bit, and
  expect-RED accepted any nonzero status rather than the RED verdict.
- Validation: fulltest **1064/0/0TO/9skip**, EXE **1026/0**, OBJ **1026/0**, zero
  warnings under `-Werror`, `forest_bind_gate` **26/26**, trailer gate 438/0, and
  all three pack lanes green at the baselined numbers.
