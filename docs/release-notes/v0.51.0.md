# Release v0.51.0 — 2026-07-26

Forest carriers **S6: `madc.ini`** — the optional configuration file, and with
it the **forest-carriers track is complete**. madc now resolves settings
**CLI > environment > madc.ini > baked defaults**, filling the last slot the S3
discovery chain reserved: the config file's `forest` key is discovery **arm 5**.
The reader is small, strict, dependency-free, and — because a config reader is
substrate, not a compiler feature — schema-blind, so madcdat and madcdis-based
tools reuse it rather than copying a parser.

- **`madc.ini`, with one visible precedence point.** Keys: `std` (default
  dialect), `forest` (a frozen-forest container — discovery arm 5, the last
  arm), `include` (repeatable extra include dirs, searched after every `-I`),
  and `cpu-limit` / `mem-limit` (defaults for `MADC_CPU_LIMIT` /
  `MADC_MEM_LIMIT`). The rule is enforced in one place rather than spread
  across consumers: the command line has already been parsed when the file is
  applied, and each environment variable is read at its use site *before* the
  ini value.
- **Lookup: `./madc.ini` → `$XDG_CONFIG_HOME/madc/madc.ini` →
  `<sysconfdir>/madc.ini`**, and the *first existing file wins outright*.
  Configuration files are never merged — a merged chain makes "why is this
  setting on?" unanswerable. Relative paths resolve against the config file's
  own directory; a leading `~/` expands.
- **Strict by design.** An unknown key, a foreign section, a missing `=`, an
  empty value, or an unparsable number/boolean is a hard error naming file:line
  and the accepted keys. A config file is the user's own file, so half-applying
  it is exactly the silent degradation this project refuses: `mem-limit = 8G`
  says so instead of quietly arming an 8 MB guard.
- **`--config=<file>` and `--no-config`.** The named file is the whole search
  and it must load — a named file that gets ignored is the same failure as a
  named forest container that gets ignored. `--no-config` skips the search
  entirely (build systems and test harnesses should pass it); the two together
  are a contradiction and refuse.
- **The reader is schema-blind and shared.** `madc::cfg::config_file` owns the
  format — lookup chain, grammar, path semantics, diagnostics — and each
  consumer registers the keys it accepts. It is the same split
  `madcdis/snapshot.h` makes for the pool container (content-blind, with
  consumer-defined `kind`s): `config_file("madcdat")` reads `madcdat.ini`,
  accepts a `[madcdat]` section, and its unknown-key diagnostic lists *its*
  keys. Nothing in the reader knows a madc key spelling.
- **No new dependency.** The grammar is `key = value` for flat scalars, the code
  reads a file an attacker may influence in a sandboxed deployment (so it is
  sized to be auditable), and a template-heavy TOML/YAML header would raise the
  self-hosting bar for every file under `src/`.
- **It is a `madc(1)` feature, by design.** `libmadc` never reads a
  configuration file — one that can redirect where the compiler loads frozen
  state from is an attack surface for a sandboxed host. The CLI passes the
  forest path down through the registration policy, where arm 5 sits inside the
  same `enable_external_forest` gate as the sidecar and environment arms.
  `configure --disable-config-file` removes madc's lookup entirely: such a build
  never searches for nor opens a `madc.ini`, and `--config=` refuses, naming the
  option.
- **Suite and pack hermeticity.** `scripts/run_tests.sh` passes `--no-config` on
  every madc invocation, and so do both forest-pack scripts: an ambient
  `madc.ini` carrying a `std` or `include` key would otherwise change the frozen
  corpus's producer config, after which every ordinary compile would fall
  through the dialect gate.
- **Fixed: the installed `madcdis/snapshot.h` did not compile downstream.** It
  names `PchCompression` in its public signatures, but `madc_pch.h` was never
  installed. It now is (it is self-contained), verified by staging an install
  and compiling a consumer that includes only `<madcdis/snapshot.h>`.
- **Fixed: `docs/build.md` still documented asmjit** — the removed x86-64 JIT
  was listed as a build requirement, with install-from-source instructions and
  `-lasmjit` in the flag table, while the MIR fork, `./configure` and its axes,
  the per-mode build targets, and the real object/test-binary paths were absent
  or wrong.
