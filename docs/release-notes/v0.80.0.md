# Release v0.80.0 — 2026-08-14

The POSIX target surface arrives for Win64: `setenv`/`unsetenv`, `strndup`,
the `timer*` gaps, and `<dlfcn.h>` served as a whole provider rather than a
supplement, all delivered through a target-tagged `libmadc_rt` archive whose
ownership is gated. Alongside it, the duplication audit that precedes every
merge caught a silent wrong answer before it shipped, a two-day cross-build
break surfaced in a mode no validation lane was building, and the project
stopped tolerating compiler warnings anywhere — backed by a mechanism rather
than a convention.

- **POSIX P1/P2 for Win64.** `setenv`/`unsetenv` ride the CRT's `_putenv_s`,
  not `SetEnvironmentVariableA` — the latter updates the Win32 environment
  block without the CRT's view of it. `<dlfcn.h>` is the first **whole
  provider**: mingw ships no such header, so madc's `posix/` entry is the
  header itself, decided on the walk's actual outcome rather than a predicted
  one.
- **A third target-property owner.** `TargetOS` / `target_windows()` joins
  `target_llp64()` and `target_microsoft_bitfields()`, so "is this target the
  non-POSIX one" has exactly one owner and no consumer re-tests `_WIN32`.
- **`__has_include` now agrees with `#include`.** The whole-provider decision
  happened after the filesystem walk, where the probe could not see it — so
  `__has_include(<dlfcn.h>)` said no on Win64 while the include worked. The
  canonical portability idiom took the wrong branch on a target that has
  dlfcn. One predicate, two consumers, same position in the resolution order.
- **The cross-* build modes are gated.** A missing include had left them
  uncompilable for two days, across a release, while all five suite lanes
  were green — those modes are how the macOS release artifacts are built.
  `check-cross-mode-compiles.sh` derives its TU list from the code and was
  negative-controlled in both directions before being wired in.
- **Zero warnings on every lane, enforced by `-Werror`.** Six build lanes
  rebuild clean at zero: host `-O0`, release `-O2`, debug,
  `hosted-x86-64-windows`, and both macOS hosted/cross pairs. The escape
  hatch is `WERROR=0`, documented as a way to get unblocked and never a way
  to land code that warns.
- **The emitted-code warning ratchet is back to all-zero.** Its last entry
  was stale: a ratchet only forbids increases, so it had been reporting green
  over a goal already met, printing `tests improved : 1` on every run.
- **Warnings that were real defects.** `-Wformat-truncation` flagged buffers
  with 19 bytes of room for a 20-digit conversion; `-nostdinc++` rode the
  `-x c` runtime compiles, putting a C++ standard library's include directory
  on a C compile's *system* path where its wrappers can shadow real C
  headers.
- **`ARFLAGS ?= rcs` was a silent no-op.** `?=` does not override a make
  *built-in* — origin is `default`, never `undefined` — so every archive had
  been built `rv`. The same trap still hides `CC`/`CXX`, which is why the
  host builds with g++ though the Makefile declares clang.

Validation at `63f008ad`: `fulltest` 1040/0/0/9, libc++ JIT 1036/0/0/13,
native EXE 1009/0, OBJ 1009/0, hosted Win64 under persistent Wine 998/0/0/51,
plus `-Werror` clean rebuilds of all six build lanes at zero warnings each.
