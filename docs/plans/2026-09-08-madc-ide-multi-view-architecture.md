# MAD C IDE Multi-View Architecture

## A Generalized System for Viewing, Comparing, and Debugging Software Across Representations

## Overview

A modern development environment should not assume that source code has only one meaningful representation.

A single section of software may exist simultaneously as:

- original source
- parsed syntax
- lowered intermediate source
- emitted C
- emitted C++
- translated source in another language
- compiler intermediate representation
- generated assembly
- externally generated assembly
- disassembled machine code
- raw binary bytes
- historical source
- previous edit states
- live debugger state

Traditional IDEs usually expose these through separate tools or specialized modes.

The MAD C IDE should instead treat all of them as instances of one fundamental abstraction:

> **A View is a representation of some portion of project state.**

Any compatible View should be capable of appearing beside any other View.

This transforms split-screen editing from a handful of predefined layouts into a general-purpose system for examining the same software from different perspectives.

---

# 1. The Core Principle

The fundamental rule is:

> **Every meaningful representation of project state should be viewable, comparable, and correlated with every other representation whenever a relationship can be established.**

A developer should not need a special-purpose feature for:

```text
source vs assembly
```

and another for:

```text
Git revision vs current source
```

and another for:

```text
MAD C output vs GCC output
```

Instead, the IDE should understand:

```text
View A ↔ View B
```

The two Views may then be displayed:

```text
side-by-side
stacked
tabbed
diffed
linked
synchronized
```

The same model can naturally extend to three or more simultaneous Views.

---

# 2. View Categories

The IDE may expose many kinds of Views.

The following categories provide an initial taxonomy.

---

# 3. Source Views

Source Views represent human-readable program source at different stages or in different syntactic forms.

Possible Views include:

```text
Original Source

Preprocessed Source

Normalized Source

MC11 / Lowered C

Emitted C

Emitted C++

Alternate-Language Projection
```

An alternate-language projection might show how a piece of code would appear using another supported source syntax while preserving the same underlying semantics.

For example:

```text
Original C++
        ↕
TypeScript-like View
```

or:

```text
Original TypeScript
        ↕
MAD C C++ View
```

This becomes particularly useful if MAD C evolves toward multiple source syntaxes lowering into a shared semantic representation.

---

# 4. Semantic Views

Semantic Views expose the program at levels above or alongside textual source.

Possible Views include:

```text
AST

Symbol Tree

Type Information

Call Graph

Dependency Graph

Control-Flow Graph

Data-Flow Graph

Reference Graph

Inheritance Graph
```

These are not merely static reports.

They should remain synchronized with the live code model.

Selecting a symbol in one View can highlight its corresponding representation in another.

---

# 5. Compiler Intermediate Views

Compiler internals should be first-class Views.

Examples include:

```text
MC11

MIR

MIR Named Opcodes

Internal Lowered Representation

Optimization Pass Output
```

Where useful, multiple compiler stages could be exposed independently.

For example:

```text
Source
   ↓
AST
   ↓
MC11
   ↓
MIR before optimization
   ↓
MIR after optimization
   ↓
Generated machine code
```

Each stage becomes inspectable rather than hidden inside the compiler.

This is particularly valuable for compiler development, debugging, education, and optimization work.

---

# 6. Generated Assembly Views

The IDE should expose the machine-level representation generated internally.

Possible Views include:

```text
GEN-ASM
```

where **GEN-ASM** is the disassembled representation of machine code generated by MIR for the current native CPU.

For example:

```asm
mov     rax, rbx
add     rax, 4
call    0x401230
```

This View should map directly back to:

```text
MIR instructions
AST nodes
source expressions
symbols
binary byte ranges
```

---

# 7. External Compiler Assembly Views

The IDE should also support assembly produced by external compiler toolchains.

Examples include:

```text
GCC Assembly

Clang Assembly

MSVC Assembly

Other External Compiler Assembly
```

These may be generated using mechanisms analogous to:

```text
gcc -S
clang -S
```

or their platform equivalents.

This allows direct comparison between MAD C code generation and established compilers.

For example:

```text
┌──────────────────────┬──────────────────────┐
│ MAD C GEN-ASM        │ GCC ASM              │
│                      │                      │
│ ...                  │ ...                  │
└──────────────────────┴──────────────────────┘
```

or:

```text
┌──────────────────────┬──────────────────────┐
│ MAD C GEN-ASM        │ Clang ASM            │
└──────────────────────┴──────────────────────┘
```

This can become an extremely useful compiler-development tool.

---

# 8. Disassembly Views

Assembly does not necessarily need to originate from source compiled inside the IDE.

The IDE should also support disassembly of:

```text
object files

executables

shared libraries

static libraries

external binaries
```

Possible Views include:

```text
Object File Disassembly

Executable Disassembly

Shared Library Disassembly
```

These Views may be generated by:

```text
internal disassembler

objdump

llvm-objdump

platform debugger APIs

other external tools
```

This allows comparison such as:

```text
MAD C source
      vs
external executable disassembly
```

or:

```text
MAD C generated code
      vs
existing system library implementation
```

---

# 9. Binary and Hex Views

The lowest-level representation should also be available.

Possible Views include:

```text
Raw Hex

Machine-Code Bytes

Object-File Hex

Executable Hex

Memory Hex
```

For example:

```text
00000000  55 48 89 E5 48 83 EC 20
00000008  E8 7B FE FF FF 48 89 C3
```

The View should ideally understand structured binary formats where applicable.

For example:

```text
ELF

PE

Mach-O
```

A binary View might expose:

```text
sections

symbols

relocations

imports

exports

debug information

machine-code ranges
```

rather than functioning only as a raw hex editor.

---

# 10. Historical Views

The same generalized View model should apply to history.

Git history should not be treated as an entirely separate subsystem.

Possible historical Views include:

```text
Current Source

Git Revision

Parent Revision

Branch Revision

Tag / Release Revision

Git Diff

Merge Diff
```

For example:

```text
┌────────────────────────┬────────────────────────┐
│ v1.0                   │ Current                │
│                        │                        │
│ source                 │ source                 │
└────────────────────────┴────────────────────────┘
```

or:

```text
Feature Branch
      vs
Main Branch
```

The same concept can apply to:

```text
AST vs historical AST

MC11 vs historical MC11

ASM vs historical ASM
```

This means a developer could examine whether a source change altered code generation.

---

# 11. Edit History Views

Git history is only one form of history.

The IDE should separately retain **editing history**.

Possible View states might include:

```text
Current

Previous Edit

5 Minutes Ago

Before Refactor

Before Agent Change

Before Build Failure

Last Successful Build

Last Test-Passing State
```

For example:

```text
┌────────────────────────────┬────────────────────────────┐
│ Before Agent Modification  │ Current                    │
│                            │                            │
│ ...                        │ ...                        │
└────────────────────────────┴────────────────────────────┘
```

or:

```text
┌────────────────────────────┬────────────────────────────┐
│ Last Passing Build         │ Current                    │
└────────────────────────────┴────────────────────────────┘
```

This effectively creates a **temporal debugger for source editing**.

Git answers:

> What was committed?

Edit history answers:

> What happened while I was working?

Because Nexus activity can be event-driven, editing states can naturally become part of the project's temporal history.

---

# 12. Diff as a General Operation

Diff should not be limited to text files.

If two Views represent comparable states, the system may offer an appropriate difference representation.

Examples include:

```text
Source Diff

AST Diff

Symbol Diff

MC11 Diff

MIR Diff

Assembly Diff

Binary Diff

Git Diff

Edit-History Diff
```

For example:

```text
MIR before optimization
        vs
MIR after optimization
```

or:

```text
MAD C generated ASM
        vs
GCC generated ASM
```

or:

```text
Current executable
        vs
previous release binary
```

This allows comparison to become a universal concept rather than a Git-specific feature.

---

# 13. Correlated Views

The most important feature of the system is not merely displaying multiple Views simultaneously.

The Views should understand their relationships.

For example:

```text
Source Token
    ↕
AST Node
    ↕
MC11 Node
    ↕
MIR Instructions
    ↕
Generated Machine Instructions
    ↕
Binary Bytes
```

All of these may represent the same underlying operation.

Suppose the original source contains:

```cpp
foo(a);
```

Selecting it may automatically highlight:

```text
AST
  CallExpression
```

```text
MC11
  lowered call node
```

```text
MIR
  call foo
```

```asm
GEN-ASM

call 0x401230
```

```text
HEX

E8 7B FE FF FF
```

The mapping should work in both directions.

Selecting the machine instruction could reveal:

```text
Generated from

source.cpp:418

Symbol
  foo()

AST
  CallExpression

MIR
  call foo

Machine bytes
  E8 7B FE FF FF
```

This is much more powerful than merely displaying a disassembler beside an editor.

# 14. Representation Lineage

It is useful to think of transformations as a lineage graph.

For example:

```text
                    Original Source
                           │
                           ▼
                          AST
                           │
                           ▼
                          MC11
                           │
               ┌───────────┴───────────┐
               ▼                       ▼
          Emitted C               Emitted C++
               │
               └───────────┬───────────┘
                           ▼
                          MIR
                           │
                           ▼
                      Machine Code
                           │
                           ▼
                        GEN-ASM
```

External compilers form parallel branches:

```text
Original Source
       │
       ├──── MAD C ───── MIR ───── GEN-ASM
       │
       ├──── GCC ───────────────── GCC ASM
       │
       └──── Clang ─────────────── Clang ASM
```

External binary artifacts may enter the graph independently:

```text
External Executable
        │
        ▼
    Disassembly
        │
        ▼
      Hex
```

The Nexus can retain whatever correlation information is available between these representations.

# 16. View Synchronization

Views should support optional synchronization.

Possible synchronization modes include:

```text
Cursor Synchronization

Selection Synchronization

Active Symbol Synchronization

Scroll Synchronization

Diff Synchronization

Execution Synchronization

Breakpoint Synchronization
```

For example:

```text
☑ Sync Selection

☑ Sync Active Symbol

☐ Sync Scrolling

☑ Sync Debugger Position
```

Some View combinations may synchronize naturally.

Others may synchronize semantically rather than line-by-line.

For example:

```text
Source ↔ ASM
```

should generally synchronize by:

```text
symbol

expression

instruction mapping
```

rather than by scroll percentage.

---

# 17. Debugging as a Property of Views

Debugging should not require an entirely separate conceptual interface.

Instead, debugger state can be projected into existing Views.

For example, execution may simultaneously appear as:

```text
SOURCE

▶ value = calculate(foo);
```

```text
MC11

▶ lowered calculate call
```

```text
MIR

▶ call calculate
```

```asm
GEN-ASM

▶ call 0x00007ff712301820
```

```text
HEX

▶ E8 4B 16 00 00
```

All are different representations of the same current execution position.

---

# 18. Debugging at Multiple Abstraction Levels

Because Views may expose several compilation layers, stepping should also be capable of operating at different abstraction levels.

Possible commands include:

```text
Source Step

Source Next

MIR Step

MIR Next

Instruction Step

Instruction Next
```

Different users may want different levels.

An application developer normally wants:

```text
Source Step
```

A compiler developer may want:

```text
MIR Step
```

A low-level systems developer may want:

```text
Instruction Step
```

The same debugger engine can expose all three through different Views.

# 22. A Core View Abstraction

Conceptually, a View might be described by a small set of attributes.

For example:

```text
View

subject
representation
revision
generator
runtime_context
```

A source View might be:

```text
subject
  Session::refresh()

representation
  C++ source

revision
  current
```

A historical source View might be:

```text
subject
  Session::refresh()

representation
  C++ source

revision
  git:a81f42
```

An assembly View might be:

```text
subject
  Session::refresh()

representation
  assembly

generator
  MAD C / MIR

target
  x86-64
```

An external compiler View might be:

```text
subject
  Session::refresh()

representation
  assembly

generator
  clang

target
  x86-64
```

A binary View might be:

```text
subject
  madc.exe

representation
  hex

revision
  current build
```

This keeps the layout system independent of specific compiler stages.

# 24. Correlation Maps

View Providers should be able to expose mappings between representations.

For example:

```text
Source Range
     ↕
AST Node ID
     ↕
MC11 Node ID
     ↕
MIR Instruction Range
     ↕
Machine Address Range
     ↕
Binary Offset Range
```

A correlation map may be:

```text
exact

approximate

one-to-one

one-to-many

many-to-one
```

For example, one source statement may generate several machine instructions.

An optimized expression might disappear entirely.

The system should preserve these relationships without pretending that every transformation remains perfectly reversible.

# 25. Compiler Comparison

One particularly useful application is direct compiler comparison.

The IDE could expose commands such as:

```text
Compare Code Generation
```

which might automatically produce:

```text
┌────────────────────┬────────────────────┬────────────────────┐
│ MAD C              │ GCC                │ Clang              │
│                    │                    │                    │
│ generated ASM      │ generated ASM      │ generated ASM      │
└────────────────────┴────────────────────┴────────────────────┘
```

Possible associated metrics include:

```text
instruction count

code size

stack usage

branches

calls

register usage

generated binary size
```

This could become an especially powerful tool for validating and improving MAD C code generation.

---

# 26. Historical Code-Generation Comparison

Because Git and compiler Views participate in the same system, it becomes possible to compare compiler output over time.

For example:

```text
MAD C v0.98 source
        vs
MAD C current source
```

or:

```text
Generated ASM at commit A
        vs
Generated ASM at commit B
```

This may reveal that a small compiler modification caused:

```text
larger generated code

extra branches

different register allocation

different calling convention behavior
```

The IDE therefore becomes useful not only for application development, but for studying the evolution of the compiler itself.

# 29. Relationship to the Nexus

The generalized View system fits naturally into the Project Nexus.

The Nexus stores or derives:

```text
source state

semantic state

compiler state

historical state

runtime state

project-management state

agent state
```

Views are projections of that state.

Conceptually:

```text
                    PROJECT NEXUS
                         │
        ┌────────────────┼────────────────┐
        │                │                │
    Historical       Semantic         Runtime
      State            State           State
        │                │                │
        └────────────────┼────────────────┘
                         │
                       VIEWS
                         │
              ┌──────────┼──────────┐
              │          │          │
             GUI        TUI        API
```

This produces a clean distinction:

> **The Nexus owns project state.**

> **Views present project state.**

The editor itself becomes one especially important kind of View.

---

# 30. Broader Design Philosophy

Traditional programming environments tend to assume:

> The source file is the program.

A Nexus-based environment takes a broader position:

> The source file is one representation of the program.

The same software also exists as:

```text
syntax

semantics

compiler IR

generated machine code

runtime behavior

history

intent

future work
```

A modern IDE should allow developers to move fluidly between those representations.

The system should therefore avoid hard-coding concepts such as:

```text
source editor

assembly window

Git diff window

debugger window
```

as unrelated tools.

Instead, all should be understood as:

> **Views onto the evolving state of the software project.**

---

# Conclusion

The MAD C IDE View system should provide a generalized mechanism for inspecting software at any useful level of abstraction.

A developer may simultaneously examine:

```text
Original Source
MC11
MIR
GEN-ASM
External ASM
Disassembly
Machine-Code Bytes
Historical Source
Runtime State
```

and freely compare them.

The key feature is not simply arbitrary split panes.

It is **semantic correlation**.

The IDE should understand that:

```text
source expression

AST node

lowered representation

MIR instruction

machine instruction

binary bytes
```

may all describe the same piece of software.

That relationship can then power:

```text
navigation

comparison

debugging

breakpoints

diffing

history

compiler analysis

AI reasoning
```

The result is a development environment in which a program is no longer presented as a single stream of source text.

Instead, the developer can inspect the software simultaneously across its many representations—from original intention and source code all the way down to individual machine bytes.

> **A program has many representations. The IDE should make all of them first-class Views of the same underlying project state.**
