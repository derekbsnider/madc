## 3. NEXT WORK — the two macOS MIR-cache blob causes ← START HERE

**Both darwin arches ship with NO MIR module cache**, while linux packs 467 KB
and win64 497 KB. Correctness survives (`consumers fall back`) — which is exactly
why the pack exits 0 — but every consumer compile on macOS pays full compile
price, which puts this next to #25. It is pre-existing (byte-identical before and
after v0.84.0's code changes) and now **gated** at `darwin mir-blob-skips 1`, so
it cannot grow and cannot be forgotten.

```
arm64:   MIR error during module compile: wrong result type in proto proto138
x86-64:  func duration_double_std____1__ratio_1_1000000000___operator%=:
         in instruction 'umods': unexpected operand mode for operand #1.
         Got 'ldouble', expected 'int'
```

- **x86-64** is the tractable one. `%` on a floating duration rep is ill-formed
  C++, so two candidate layers: (a) whichever pass speculatively instantiates
  `duration<double, nano>::operator%=` during the pack, and (b) the `%` lowering
  choosing an integer opcode from a floating operand type. Reducer shape: a
  `duration<double, nano>` `%=` in a libc++ TU. **Fix (b) if it is (b)** — an
  integer modulo emitted for a floating operand is wrong wherever it comes from.
- **arm64** names no source function, so dump the module to localize
  `proto138` first.

Lower `darwin mir-blob-skips` to 0 in the same commit that fixes them; the gate
prints the exact number when a run comes in under baseline.

Then: **#60** macOS headerless cell (`sandbox-exec` denying the SDK subpath) —
it is also #63's darwin consumer-side proof. Then #25 lazy decompression, #61
pointer-to-member-function remainder, #56 follow-ons, #55, #49 branch pruning.

## 5. The gate — what it is, and the two things not to "simplify"

Full design: **`docs/plans/2026-08-17-pack-degradation-gate.md`**. One owner,
`scripts/forest_pack_gate.sh`; three pack scripts call it; baselines are per
profile and a missing line means ZERO allowed.

- **The `materialize filter:` marker requirement is load-bearing.** Every
  load-side diagnostic is `DBG`-gated, so a load log from a run that bound
  nothing holds zero of everything. Without the marker the gate would report
  success for a test it never ran. Any counter added later needs the same guard.
- **`kind=0` RATCHETS, and it must not be "tightened" to a hard zero.** The
  previous handoff specified hard zero on the premise that a DK_NONE has no
  legitimate instance. It has: 55 of the 57 measured are DEPENDENT operands
  (`ref _Tp*`, `allocator__Tp1*`, `polymorphic_allocator__Up*`) — a pointer to a
  template parameter has no concrete record by construction and the consumer
  re-instantiates from the pattern. A hard zero would have gone red on day one
  on correct code. What hard-zeroes instead is `materialize fill: DROPPED` and
  `forest_restore_decls: SKIPPED`, and a ratchet still catches #64 (its nested
  enum ADDED one).

`scripts/mac_battery.sh` leg 3c carries a DUPLICATE of the token strings on
purpose — it runs on a Mac from an unpacked tarball with no repo — and
`--selftest` leg 11 fails if that copy drifts. Update both together.
