# madcdis: Core Data Substrate Plan

## Status

Active design track. `madcdis` is the typed in-memory data substrate
that ships as part of core `libmadc`. It supersedes the earlier
`madcdat-plan.md` framing in which the entire data subsystem was
optional; the new discipline is that the substrate is core and only
external drivers are optional.

This plan is paired with the revised `madcdat-plan.md`, which now
covers only the external driver bundle that depends on `madcdis`.

## Name and Boundary

`madcdis` ("madc data internal substrate") is the core/internal half
of the data system. It lives inside `libmadc` and is available to
every Mad-C program without an opt-in dependency.

`madcdat` is the optional companion library that adds external
storage and service drivers on top of `madcdis`. It depends on
`madcdis`; `madcdis` does not depend on it.

The naming pair is intentional: `dis` is the local/internal substrate,
`dat` is the external-data driver bundle. Headers split accordingly:

- core headers under `include/madcdis/`
- driver headers under `include/madcdat/`
- `madc::DataSource` stays in `include/libmadc/` because it is a
  general external-conduit abstraction broader than storage

## Intent

Every Mad-C program should have access to a typed in-memory data
substrate without depending on external drivers. The substrate must:

- own the language's data model (datasets, relations, indexes,
  query IR, planner)
- ship with `mem://` and `shm://` drivers built on memory pools
- support graph-relational queries (GQL, SQL, Cypher) as first-class
  language syntax via namespaced sub-grammars
- define the abstract `DataDriver` contract that external drivers
  implement
- be useful entirely on its own, with no `libmadcdat` link required

External storage and services live in `madcdat` and plug into the
same `madcdis` substrate via the `DataDriver` interface and the
`DataDriverRegistry`.

## Non-Goals

- No external storage drivers in `madcdis` itself (those live in
  `madcdat`).
- No textual SQL/Cypher/GQL parsing as a runtime library function
  with stringly-typed queries. Native query syntax is a compiler
  feature; runtime parser entry points exist as a convenience for
  genuinely dynamic queries but are not the primary surface.
- No required external dependencies for `mem://` or `shm://`. Pool
  storage uses standard POSIX shared-memory primitives where
  available; everything else uses the platform allocator.
- No global garbage collection. Pool-scoped lifetime management,
  optional ref-counting per object, and optional tracing GC per
  pool — never a process-wide GC.

## Core Principles

### 1. The substrate is core, not optional

Datasets, relations, query IR, the planner, and in-memory drivers
ship as part of `libmadc`. A Mad-C program can declare
`DataSet<Room> rooms("mem://world")` and run GQL queries against it
without linking any optional library. This is the baseline
capability of the language, not an extension.

### 2. Memory pools are the allocation primitive

All `madcdis`-managed memory comes from pools. Pools are typed,
sized, scoped, and droppable:

- bump-pointer allocation with O(1) wholesale drop
- optional per-type slab allocation for known-size records
- optional ref-counted objects within a pool
- optional tracing GC over a pool's contents
- position-independent addressing for cross-process sharing
- snapshot/restore for persistence handoff to `madcdat` drivers

Pool drop is the canonical bulk-cleanup operation. Per-object free
is supported but discouraged for pool-allocated data; the pool's
lifetime is the unit of memory management.

### 3. `mem://` and `shm://` are pool-backed drivers

Both schemes implement the same `DataDriver` interface and share a
common pool implementation. The difference is the backing memory:

- `mem://` allocates from the process heap
- `shm://` allocates from a POSIX shared-memory segment

Both support the full local execution capability set (scans, point
lookups, range lookups, filter/project/sort/limit pushdown). The
`shm://` driver additionally supports cross-process attach and
position-independent data structures.

Pool format is stable enough to be opened by multiple processes
simultaneously when backed by `shm://`. Schema versioning is part
of the pool header; mismatched attach attempts fail cleanly.

### 4. GQL is the canonical query language

The Query IR is shaped to faithfully represent GQL semantics
(ISO/IEC 39075). GQL is the only query language that natively
expresses graph patterns, tabular operations, and the composition
between them, which matches Mad-C's `Relation<A,B>` plus
`DataSet<T>` data model directly.

SQL and Cypher are supported as sub-grammars that lower to the
same Query IR. They exist for compatibility with users' existing
mental models, not because they are semantically distinct.

The builder API (`madc::query()`) is the third front-end, producing
the same Query IR programmatically.

### 5. Native query syntax is namespaced

Query languages activate via namespace prefix on the expression:

```c
auto adults = sql::SELECT name, age FROM users WHERE age >= 18;
auto net   = cypher::MATCH (u:User)-[:FRIEND*1..3]->(f) RETURN f;
auto path  = gql::MATCH (a)-[*]->(b) WHERE a.id = 1 RETURN b;
```

The parser sees `sql::`, `cypher::`, or `gql::` followed by a
known statement keyword and yields to the corresponding
sub-grammar. The sub-grammar parses to its natural termination
and produces a Query IR expression.

This avoids reserving keywords like `SELECT` or `MATCH` in the
main Mad-C namespace. Identifiers named `select` or `match`
remain valid outside the namespaced scope.

`using namespace sql;` activates SQL keywords as bare expression
starts within a scope, for users who want shorter syntax in
SQL-heavy files.

### 6. Types stay local values

`DataSet<T>` materializes values of `T` from storage. Instances of
`T` are ordinary Mad-C values in memory, no proxy semantics, no
hidden I/O on field access. The pool owns the storage; the
dataset owns the mapping; the user owns the values they pull out.

This rules out the ActiveRecord/proxy-object pattern by design.
Updates go through explicit dataset operations; the language does
not pretend that mutation of an in-hand value automatically
persists.

### 7. Mapping is inferred first, configured second

`MapperBuilder<T>` and `MappingSpec<T>` infer schema and field
mappings from `T`'s type metadata (member names, types, sizes).
Explicit configuration is only required for keys, joins, edge
labels, custom field names, or persistence exclusions.

The type system already knows enough to drive automatic mapping
for most cases. Users who want schema-first declarations use the
`sql::create` / `cypher::create` / `gql::create` helpers (planned)
to define type and storage layout together.

### 8. Query is optional, not foundational

Direct programmatic access (`DataSet<T>::get`, `::insert`,
`::scan`, cursor iteration) is the primary API. Query syntax is
layered above it. Programs that just want typed pool storage can
use datasets without ever touching the query IR or planner.

### 9. The planner is core, capability-aware, and federation-ready

The federated planner is part of `madcdis` from V1, even when
the only drivers it sees are `mem://` and `shm://`. This means:

- federation works across in-memory pools natively
- adding external drivers (via `madcdat`) is a matter of
  registering more drivers — no planner redesign required
- driver capabilities are advertised through `DriverCapabilities`
  and the planner pushes down what each driver can honor

### 10. Indexes are derived artifacts

Indexes over pool data are owned by the dataset, not hidden state
in the storage layer. Rebuild is always possible from the canonical
data. This matches `madcdat`'s discipline for on-disk indexes
(FLR/VLR/etc.) — same principle applied to in-memory data.

### Query IR and planner

```

    plus: composition between graph and tabular results

    plan(Query, datasets) -> Plan
    execute(Plan) -> result cursor

    capability-annotated stages
    pushdown decisions
    join strategy
    local execution glue
```

### Query language parsers (compiler-level)

These are compiler frontend features, not runtime library
functions, but the runtime IR they target lives in `madcdis`.

```
sql::      sub-grammar, parses SQL statements to Query IR
cypher::   sub-grammar, parses Cypher statements to Query IR
gql::      sub-grammar, parses GQL statements to Query IR
```

All three lower to the same Query IR. The compiler resolves
identifiers in the query against the symbol table, type-checks
against bound schemas, and emits code that constructs the Query
object and dispatches to the planner.

For genuinely dynamic queries (admin REPLs, configuration-driven
queries, user-input query builders), runtime parser entry points
exist:

```
madc::parse_sql(string) -> Query
madc::parse_cypher(string) -> Query
madc::parse_gql(string) -> Query
```

These produce the same Query IR. They are convenience APIs, not
the primary surface.

## Pool Design Notes

### Allocation modes

- **Bump-pointer** (default): allocations advance a pointer; drop
  resets it. O(1) drop regardless of allocation count.
- **Slab** (per-type): fixed-size cells with a free list. Fast,
  no fragmentation, suitable for record arrays.
- **General-purpose**: size-class buckets, fragmentation-aware.
  Used for variable-size data (strings, MadValues holding
  arbitrary content).

A pool may use any combination of these for different sub-arenas
within it.

### Drop semantics

Drop is wholesale: all allocations from the pool become invalid
simultaneously. Three flavors:

- **POD drop**: no destructors run, raw memory reclamation. Fast.
- **Typed drop**: destructors run for non-trivial types via a
  registered drop hook per type. Slower but still bulk.
- **Traced drop**: GC runs over the pool before reclamation,
  finalizing reachable objects. Used only for traced-lifetime
  pools.

The pool knows which mode applies based on what was allocated
through it.

### Position-independent pointers

Pointers within a pool are stored as offsets from the pool base,
not raw addresses. `PoolPtr<T>` is the typed offset wrapper:

```c
class PoolPtr<T> {
    Pool *pool;
    uint64_t offset;
    
    T *get() { return reinterpret_cast<T*>(pool->base() + offset); }
    T &operator*() { return *get(); }
};
```

This makes shared-memory pools attach-portable: process A and
process B can map the same `shm://` segment at different
addresses and still navigate the data correctly. The cost is one
extra add per dereference, which is negligible in practice.

### Synchronization for shm://

Shared-memory pools use:

- **Robust futex-based mutexes** for critical sections (so a
  crashed process holding a lock doesn't deadlock survivors)
- **Lock-free where possible** (single-producer queues, sharded
  hash tables, RCU-style updates for read-heavy structures)
- **Reader-writer locks** for indexes that see many readers and
  occasional updates

Cross-process atomic operations require proper alignment, which
is part of the pool allocation contract.

### Persistence handoff

Pool snapshot writes the pool's bytes to a stream in a stable
format (versioned header, payload, optional checksum). Restore
reads the same format back. This gives:

- `mem://` pools can be saved to disk and reloaded later
- `shm://` pools survive process restart by remaining in shared
  memory; saving is for cold backup or migration
- `madcdat` file drivers (`file://`, `flr://`, `vlr://`) consume
  pool snapshots as one of their input formats

The snapshot format is not coupled to any external storage
format. `madcdat` drivers translate between snapshot bytes and
their on-disk representations.

## Federation and Planner

The federated planner is part of `madcdis` from V1 and works
across in-memory pools natively. The planning pipeline:

1. **Query input** — Query IR from any front-end (sql::,
   cypher::, gql::, builder, runtime parser).
2. **Logical IR** — normalized representation, datasets resolved
   to driver-backed sources.
3. **Binding/relation resolution** — relations expanded into
   join/traversal stages.
4. **Driver capability annotation** — each stage tagged with
   which drivers can handle it.
5. **Pushdown planning** — push stages to capable drivers; keep
   ungrouped stages for local execution.
6. **Physical plan** — concrete execution graph.
7. **Cursor execution** — pull-based iteration with local glue
   handling cross-driver joins.

For `madcdis` alone, federation happens across in-memory pools
(e.g., one `mem://` pool of users joined with one `shm://` pool
of sessions). Adding `madcdat` drivers expands the set of
sources the planner can federate over without changing the
planning logic.

### In-memory driver capabilities

`mem://` and `shm://` drivers advertise full capability support:

- `read`, `write`, `scan`, `point_lookup`, `range_lookup`: yes
- `filter_pushdown`, `project_pushdown`, `sort_pushdown`,
  `limit_pushdown`: yes (executed during iteration)
- `join_pushdown`: yes (for joins within the same pool)
- `graph_match`, `edge_expand`, `path_search`: yes (using
  `Relation<A,B>` declarations as edges)
- `transaction`: limited at V1 (single-driver write-through),
  expanded in later phases
- `soft_delete`: yes (tombstone support in pool storage)

External drivers in `madcdat` advertise narrower capabilities;
the planner picks up the slack locally.

## Mad-C Compiler Integration

`madcdis` is the runtime side. The compiler side adds:

- **Lexer recognition** of `sql::`, `cypher::`, `gql::` as
  sub-grammar entry points when followed by a statement keyword
- **Sub-grammar parsing** via Gecko grammars for each query
  language
- **Lowering passes** from each sub-grammar AST to Query IR
- **Symbol resolution** for dataset and field identifiers inside
  query expressions
- **Type checking** against bound `SchemaInfo` for projection and
  predicate types
- **`using namespace sql;` / `using namespace gql;` etc.** to
  activate bare keywords in a scope

The compiler also provides:

- **`sql::create` / `cypher::create` / `gql::create`** — schema
  declarations that produce both Mad-C type definitions and
  `StorageBinding` metadata, compiled together.
- **Result type inference** — `auto users = gql::MATCH ...
  RETURN u.name, u.age` infers a typed result from the RETURN
  clause and the schema.

These are compiler features that consume `madcdis` runtime types;
they ship together because the language and runtime co-evolve.

## Delivery Phases

### V1 — Pool substrate and in-memory drivers

Land:

- `madc::Pool` with mem and shm backing
- `madc::PoolPtr<T>`, `madc::TypedPool<T>`
- `MemPoolDriver`, `ShmPoolDriver`
- `DataSet<T>`, `Cursor<T>`, `Relation<A,B>` migrated from
  current `madcdat/` to `madcdis/`
- `SchemaInfo`, `MappingSpec<T>`, `DataMapper<T>` migrated
- `DataDriver` interface and registry migrated
- `Query` IR (current flat form retained, GQL extensions pending)
- `QueryBuilder` (current code, retained)
- Programmatic API only (no native query syntax yet)

Outcome: every Mad-C program can construct typed in-memory and
shared-memory datasets, relate them, scan them, query them via
the builder API, and persist them via snapshot/restore.

### V2 — Query IR redesign for GQL

Land:

- Extended Query IR supporting graph patterns, path expressions,
  tabular operations, and composition
- `QueryPlanner` with capability-aware pushdown
- In-memory federated planning across `mem://` and `shm://`
- Builder API extensions for graph patterns and paths

Outcome: builder API expresses full GQL semantics; planner
federates across in-memory pools.

### V3 — Native query syntax

Land:

- Gecko grammars for SQL, Cypher, GQL sub-languages
- Compiler lexer and parser recognize `sql::`, `cypher::`,
  `gql::` namespaced sub-grammars
- Lowering passes from sub-grammar ASTs to Query IR
- Symbol resolution and type checking in query expressions
- `using namespace sql;` etc. for bare-keyword activation
- Runtime `madc::parse_sql/cypher/gql` entry points for dynamic
  query strings

Outcome: Mad-C programs use native query syntax that compiles to
the same IR as the builder API, with compile-time type checking
against bound schemas.

### V4 — Schema declaration helpers

Land:

- `sql::create`, `cypher::create`, `gql::create` as combined
  type + storage binding declarations
- Result type inference for query expressions
- Optional ORM-style `Record<T>` base class for users who want
  ActiveRecord-shape APIs (lowering to the same substrate)

Outcome: schema-first workflows are first-class; users can
declare data shape in their preferred query language and get
Mad-C types and storage bindings together.

### V5 — Optional GC and advanced pool features

Land:

- Optional tracing GC per pool
- Pool growth policies (resizable pools)
- Per-pool snapshot/restore optimization (copy-on-write where
  supported)
- Improved cross-process synchronization primitives

Outcome: long-running server workloads with complex object
graphs get GC support; pools scale to multi-gigabyte sizes;
shared-memory deployments mature.

## Migration from current state

The current code has most `madcdis` pieces sitting in
`include/madcdat/`. Migration is mechanical:

1. **Move headers**: `madcdat/{schema,mapper,query,relation,
   dataset,driver}.h` → `madcdis/...`
2. **Update internal includes** in moved headers
3. **Add forwarding shims** under `madcdat/` for backward
   compatibility during transition
4. **Add pool subsystem** as new code (no displacement)
5. **Add `MemPoolDriver` and `ShmPoolDriver`** as new code
6. **Register in-memory drivers** in `libmadc` init
7. **Update `madcdat`** to include from `madcdis/` for interfaces
8. **Sunset forwarding shims** once all consumers updated

The existing `madcdat` driver implementations (`bdb`, `gdbm`,
`qdbm`, `sqlite`) don't change behavior; they just include from
`madcdis/` for the `DataDriver` interface and related types.

## Open Questions

- Whether `MadValue` and `madcdis::value` should unify (currently
  they appear to be the same `madc::value` — confirm and document)
- Whether the snapshot format should be versioned per pool type
  or have a single global version
- How much of GQL the V2 IR redesign should cover initially —
  full ISO/IEC 39075 or a documented subset
- Whether `shm://` should support multiple writer processes in V1
  or restrict to single-writer / many-reader initially
- How transaction semantics should work across `mem://` and
  `shm://` boundaries — single-driver only in V1, cross-driver
  in a later phase
- Whether the Gecko grammars for SQL/Cypher/GQL should be
  separate files or unified (likely separate for maintenance,
  with shared grammar fragments for common pieces like
  expressions and identifiers)

## Relationship to `madcdat`

`libmadcdat` is the optional companion library covering external
storage and services. It depends on `madcdis` and consumes:

- `DataDriver` interface (to implement file/db/service drivers)
- `Query` IR (to receive plans from the planner)
- `DriverCapabilities` (to advertise what each driver can handle)
- `DataSource` (to identify external sources)
- `SchemaInfo` and `MappingSpec<T>` (to map external records)
- Pool snapshot/restore (for file-backed pool persistence)

`madcdat` does not modify `madcdis` runtime types or extend the
core API surface. It only registers additional drivers into the
existing registry and implements `SourceAdapter` for parsing
external content formats.

See `madcdat-plan.md` for the external driver bundle plan.
