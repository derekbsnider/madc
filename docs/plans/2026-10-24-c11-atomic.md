# C11 `_Atomic` and `<stdatomic.h>` (B252)

Owner 2026-10-24: B252 goes first, ahead of the redis blockers (redis's
`atomicvar.h` picks `<stdatomic.h>` under C11). It follows the release
procedure work (`scripts/release_diff.sh`).

## Today

- `_Atomic long q;` → `use of undeclared identifier '_Atomic'`; `_Atomic(int)`
  → `Expecting identifier`. `src/madc_keywords.cpp` lists `_Atomic`, but that
  table only answers keyword provenance. The lexer's reserved words are
  `keyword_map` (`Program::add_keywords`), and `_Atomic` is not in it.
- `<stdatomic.h>`: libmadc carries none, so the release binary reads gcc's from
  disk. `forest_pack_sources.sh` excludes the compiler's include dir on purpose.
  gcc's copy needs `__auto_type` (absent) and clang's needs `__c11_atomic_*`
  (absent).
- What works: the `__atomic_*` / `__sync_*` builtins lower in
  `CirBuilder::lower_atomic_builtin` to gcc-compiled `__madc_atomic_*` helpers
  (src/va_helpers.cpp). C++ `std::atomic` over pthreads matches g++.
- c2mir accepts the `_Atomic` qualifier with no atomic codegen. It refuses
  `_Atomic(T)` and errors on every pointer-to-atomic assignment, call, return,
  subtraction and conditional. MIR has no atomic instructions.

## The canon (C11 6.2.5p27, 6.5.2.4, 6.5.16, 6.7.2.4, 6.7.3)

- `_Atomic` is a type qualifier, and `_Atomic ( type-name )` a type specifier;
  both name the same atomic type. Size and alignment may differ from the
  non-atomic type (gcc/clang x86-64: the same for 1/2/4/8; a 3-byte struct
  becomes 4).
- Lvalue conversion of an atomic object is an atomic load, seq_cst.
- Simple assignment is an atomic store, seq_cst. Initialization is NOT atomic.
- `E1 op= E2` and `++` / `--` are ONE atomic read-modify-write, seq_cst. For
  `+ - & | ^` on an integer, and `+ -` on a pointer: a fetch-op. Otherwise
  (`* / % << >>`, floating types): a compare-exchange loop (footnote 113).
- Member access of an atomic struct is undefined (6.5.2.3p5).
- Before coding, read gcc's and clang's lowering of every form on the build
  container (`gcc -S -fverbose-asm -O0`, `clang -S -O0`). On x86-64 expect:
  a load is `mov`; a store is `xchg` (or `mov` + `mfence`); `x++` with its
  value unused is `lock add`; `*=` and float `+=` are `cmpxchg` loops; a
  non-lock-free size is a libatomic call.

## Design (by layer, deepest first)

1. **Lexer.** `_Atomic` becomes a reserved word for C11+ and the madc dialect,
   as `_Thread_local` is (keyword table version gate). In C++, `_Atomic` is
   libc++'s/libstdc++'s `<stdatomic.h>` macro territory (C++23
   `_Atomic(T)` = `std::atomic<T>`): leave it an identifier there.
2. **Qualifier model.** Add `cvATOMIC` to `CvQual` (datadef.h). Widen every
   site that masks with exactly `cvCONST | cvVOLATILE`, including
   `getQualifiedType`, `modeled_cv` (C only), `cv_prefix_spelling`, the
   declarator's level cv, and the freeze record flags. Otherwise the bit is
   silently dropped.
   - The qualifier form joins `is_cv_qualifier_token` /
     `consume_declarator_stars` / the declaration-specifier flags.
   - The specifier form `_Atomic ( type-name )` reads its operand through
     `parse_type_id`, like the typeof family's `parse_typeof_datatype`.
3. **CIR.** Never emit `N_ATOMIC`: c2mir refuses pointers to atomic types.
   The object is emitted with its unqualified type, and every access to an
   atomic lvalue goes to a helper. This is the integer `_Complex` precedent
   (`as_lowered_complex` → `int_complex_binop` / `int_complex_unary`):
   - read (lvalue conversion) → `__madc_atomic_load_n` (or the object form);
   - `=` → `__madc_atomic_store_n`, and the expression's value is the stored
     value;
   - `++`/`--`/`+=`/`-=`/`&=`/`|=`/`^=` on an integer, and `+=`/`-=` on a
     pointer (scaled by the element size) → the fetch-op helpers
     (`add_fetch` for the prefix/compound value, `fetch_add` for postfix);
   - every other compound assignment → a compare-exchange loop in a
     statement expression (`m_pending_stmts` + `N_STMTEXPR`);
   - sizes other than 1/2/4/8 → the object helpers (the hashed lock path).
   Initialization stays a plain store.
4. **`<stdatomic.h>`.** An embedded `include/madc/stdatomic.h`, written over
   `__typeof__` + the `__atomic_*` builtins (no `__auto_type` needed): the
   `atomic_*` typedefs, `memory_order`, `ATOMIC_*_LOCK_FREE`,
   `ATOMIC_VAR_INIT`, `atomic_flag`, and every generic function. It joins
   the C pack layer's roots (`scripts/forest_pack_c_headers.txt` and its
   darwin / windows twins) and `tests/testfreestandingheaders.mad`. C++
   compiles keep libstdc++'s / libc++'s own `<stdatomic.h>`.
5. **Thread-safety contract.** The C11 contract itself: every access to an
   atomic object is atomic and seq_cst unless an explicit order is passed.
   Non-lock-free sizes take the helpers' address-hashed spin lock, as
   libatomic does.

## Tests

- `tests/testc11atomic.mad` (`--std=c11`, run as C): every form above on
  `_Atomic` char/short/int/long/pointer/double and a 3-byte struct, with the
  qualifier and the specifier spellings. A 4-thread × 1M increment race on
  each RMW form is the atomicity oracle. Expected output comes from gcc and
  clang.
- `tests/teststdatomic.mad`: the `<stdatomic.h>` surface, every generic
  function and order, `atomic_flag`, `atomic_is_lock_free`, the
  `ATOMIC_*_LOCK_FREE` values gcc reports.
- Refusals with gcc's diagnostics: `_Atomic` on an array or a function type,
  an `_Atomic` bit-field.
- Gate: `check-system-headers-from-libmadc.sh` proves `<stdatomic.h>` comes
  from libmadc.
